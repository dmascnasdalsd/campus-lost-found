# 校园失物招领系统 — Spec

Feature slug: `campus-lost-found`
Status: ready-for-agent
Tracker: local markdown (`.scratch/campus-lost-found/`)

## Problem Statement

校园里每天都有物品遗失与拾获，但信息极度分散：

- 失主丢了校园卡、耳机、钥匙，不知道该去哪里找，只能在 QQ 群、微信群、表白墙里发一条消息，几小时后就被刷走。
- 拾得者捡到东西后交给保卫处，保卫处登记在一张纸质登记表上，失主无法按物品名、地点、时间检索。
- 即便双方都在找对方，也缺少可信的对接渠道——口头描述物品特征就领走，冒领没有成本。
- 保卫处的登记表无法统计「哪些地点/时段高发」「多少物品真正归还」，做不了防范。

结果是大量物品堆在保卫处直到过期销毁，真正归还的比例很低。

## Solution

一个校内失物招领 Web 系统，把「失物启事」与「招领启事」放到同一个可检索的地方，并把认领撮合流程固化下来：

- 失主发布**失物启事**（LostReport）：丢了什么、什么时候、在哪丢的、特征描述、可选图片。
- 拾得者发布**招领启事**（FoundReport）：捡到什么、什么时候、在哪捡的、当前保管方式（自留 / 已交保卫处）、可选图片。
- 任何人（含未登录访客）都可按分类、地点、时间范围、关键词检索两类启事。
- 拾得者可以对自己保管的物品发起**认领申请**（Claim）；也可以反向：失主在自己的失物启事下看到「疑似匹配的招领启事」并主动联系。
- 认领走**申请 → 失主/拾得者确认 → 站内消息约定线下交还 → 标记已归还**这条链路，管理员可查看全过程以处理纠纷。
- 管理员（保卫处/学工处）负责审核违规或虚假启事、下架、置顶，并查看统计数据。

交还完成后启事标记「已归还」，从默认列表沉底，但保留可检索，供日后查证。

## User Stories

Actors：**访客**（未登录）、**用户**（已登录的在校学生/教职工，兼具失主与拾得者身份）、**管理员**（保卫处/学工处）。

### 账号与身份

1. 作为访客，我想要用校园邮箱/学号注册账号，以便发布和响应启事。
2. 作为用户，我想要用学号+密码登录，以便管理自己的启事。
3. 作为用户，我想要在登录后看到自己的昵称、所属院系与联系方式默认值，以便发布时不用每次重填。
4. 作为用户，我想要修改密码，以便账号安全。
5. 作为用户，我想要设置「默认联系方式」（手机号/微信号/邮箱）并可选择是否对他人公开，以便在不暴露隐私的前提下被联系。
6. 作为用户，我想要退出登录，以便在公共电脑上保护账号。
7. 作为管理员，我想要把某个用户标记为禁用，以便处理恶意发布。

### 发布启事

8. 作为失主，我想要发布一条失物启事，填写物品名称、分类、丢失时间、丢失地点、特征描述与可选图片，以便让别人找到我。
9. 作为拾得者，我想要发布一条招领启事，填写物品名称、分类、拾获时间、拾获地点、物品特征与可选图片，以便失主能匹配到。
10. 作为发布者，我想要物品名称支持从常见物品词表（校园卡、身份证、钥匙、耳机、手机、笔记本电脑、充电宝、水杯、书籍、雨伞、衣物、运动器材、其他）中选或自填，以便分类不会五花八门。
11. 作为发布者，我想要地点从校园地点词表（教学楼、图书馆、食堂、宿舍楼、体育馆/操场、校医院、校门、其他）中选择并可补充描述，以便按地点检索有效。
12. 作为发布者，我想要给启事上传 1～3 张图片，以便他人一眼认出物品。
13. 作为发布者，我想要在上传图片前看到本地预览，以便确认没有传错。
14. 作为发布者，我想要在提交前预览启事最终展示效果，以便确认信息完整。
15. 作为发布者，我想要在发布后 30 分钟内修改或删除自己的启事，以便纠正填错的信息。
16. 作为发布者，我想要在启事被管理员审核不通过时看到原因，以便修改后重新提交。
17. 作为发布者，我想要看到启事的浏览量，以便判断要不要补充描述。
18. 作为失主，我想要把已在自己这里找回的物品启事标记为「已归还」，以便它不再打扰别人。
19. 作为拾得者，我想要把「已交保卫处」的物品启事标记为已移交，并填写移交单号，以便失主去保卫处领取。

### 浏览与检索

20. 作为访客，我想要在首页同时看到最新的失物启事与招领启事，以便快速判断有没有自己丢的东西。
21. 作为访客，我想要在列表里按「失物 / 招领」切换，以便只看我关心的那一类。
22. 作为访客，我想要按分类筛选，以便只看校园卡或电子产品。
23. 作为访客，我想要按地点筛选，以便只看图书馆相关的启事。
24. 作为访客，我想要按时间范围筛选（今天 / 最近 3 天 / 最近 7 天 / 最近 30 天 / 自定义），以便找早期丢失的物品。
25. 作为访客，我想要按关键词搜索物品名称与描述，以便直接搜「AirPods」。
26. 作为访客，我想要在列表里看到每条启事的缩略图、物品名、地点、时间和状态徽标，以便快速扫读。
27. 作为访客，我想要点击启事进入详情页，看到完整描述、大图、发布者公开的联系方式，以便联系对方。
28. 作为访客，我想要翻页或无限滚动浏览列表，以便看更多结果。
29. 作为访客，我想要在搜索无结果时看到「发布一条失物启事」的引导，以便立刻补上信息。
30. 作为用户，我想要按「最新发布 / 最近丢失时间」排序，以便优先看到时效性高的启事。
31. 作为用户，我想要在详情页看到「疑似匹配」的同类启事列表，以便自己发现可能的配对。

### 认领撮合

32. 作为拾得者，我想要对一条失物启事发起认领申请，提交我保管的物品与可交还的时间地点，以便主动联系失主。
33. 作为失主，我想要对一条招领启事发起认领申请，说明物品的独有特征（如贴纸、划痕、序列号后四位），以便证明东西是我的。
34. 作为启事发布者，我想要在我的启事下看到所有待处理的认领申请，以便逐条处理。
35. 作为启事发布者，我想要接受某一条认领申请，以便与对方约定交还。
36. 作为启事发布者，我想要拒绝认领申请并填写拒绝对原因，以便告知申请人。
37. 作为申请人，我想要在申请被接受/拒绝时收到站内通知，以便及时跟进。
38. 作为双方，我想要在被接受后进入一个只对彼此可见的站内会话，交换联系方式并约定交还时间地点，以便安全完成交还。
39. 作为申请人，我想要在对方 7 天未处理时仍能看到申请处于「待处理」，以便不误以为已通过。
40. 作为双方，我想要在交还完成后把启事标记为「已归还」，并让对应的启事与认领申请一起关闭，以便终止撮合。
41. 作为用户，我想要撤回自己提交的、还没被处理的认领申请，以便反悔。
42. 作为用户，我想要在一条启事下最多保留一条「进行中」的认领申请，被拒后才能重新申请，以便防止刷申请。

### 我的页面与通知

43. 作为用户，我想要在「我的发布」里看到自己发过的全部启事及其实时状态，以便管理。
44. 作为用户，我想要在「我的认领」里看到我发起和收到的认领申请及其状态，以便跟进。
45. 作为用户，我想要收到站内通知（认领申请、被接受/被拒、会话新消息、启事审核结果），以便不用反复刷新。
46. 作为用户，我想要看到未读通知数角标，并能一键全部标记已读，以便快速清理。
47. 作为用户，我想要编辑自己的个人资料（昵称、院系、联系方式、公开开关），以便信息保持准确。

### 管理员

48. 作为管理员，我想要看到待审核的启事队列（含图片与描述），以便处理违规或疑似虚假内容。
49. 作为管理员，我想要通过或驳回一条启事并填写驳回原因，以便内容质量可控。
50. 作为管理员，我想要置顶某条重要启事（如「认领一批校园卡」），以便提高曝光。
51. 作为管理员，我想要下架任意启事并记录原因，以便处理举报。
52. 作为访客或用户，我想要举报一条启事或一条消息，并选择理由（虚假信息 / 广告 / 辱骂 / 其他），以便参与治理。
53. 作为管理员，我想要看到举报列表并逐个处理（驳回举报 / 下架内容 / 禁用用户），以便闭环。
54. 作为管理员，我想要查看统计看板：每日新增启事数、归还成功数、归还率、按地点与分类的分布、高发时段，以便安排防范。
55. 作为管理员，我想要把统计结果按周/月切换，以便看趋势。
56. 作为管理员，我想要导出某时间段的启事与归还记录为 CSV，以便交给上级或做线下归档。

### 通用与非功能

57. 作为用户，我想要上传大图时不至于让页面卡死（客户端压缩后再上传，单图 ≤ 5MB），以便操作顺畅。
58. 作为用户，我想要在手机上正常浏览与发布（响应式布局），以便在宿舍或路上随手发。
59. 作为用户，我想要在表单校验失败时看到具体到字段的中文提示，以便快速改正。
60. 作为访客，我想要在未登录时点击「发布」或「申请认领」被引导去登录，登录后回到原页面，以便不丢失操作意图。
61. 作为用户，我想要页面首屏在普通校园网络下 2 秒内出现内容，以便体验不差。
62. 作为管理员，我想要所有内容操作都有审计记录（谁在何时通过/下架/置顶了哪条），以便追溯。

## Implementation Decisions

### 系统边界与形态

- 单体应用：Spring Boot 后端（REST API）+ Vue 3 前端（SPA），前后端同仓分目录（`backend/`、`frontend/`）。
- 后端与前端各自独立构建；后端只提供 JSON API 与静态上传文件的读取，不做服务端渲染。
- 开发期前端通过 Vite 代理打到后端；生产期由后端或独立静态服务托管前端产物。

### 后端技术选型

- Java 17 + Spring Boot 3.x（Web、Validation、Data JPA、Security）。
- MySQL 8 作为唯一持久化存储；schema 用 Flyway 迁移管理，不用 `ddl-auto` 改表。
- 认证用 JWT（无状态）：登录颁发 access token，前端存内存 + HttpOnly refresh cookie；角色两个：`USER`、`ADMIN`。
- 图片存本地磁盘目录（可配置），数据库只存相对路径 + 原始文件名 + MIME + 大小；不引入对象存储。
- 统一响应体 `{ code, message, data }` 与统一异常处理（`@RestControllerAdvice`），业务错误用错误码而非 HTTP 5xx 表达。

### 核心领域模型

- **User**：id、学号(studentNo，唯一)、昵称、院系、邮箱、密码哈希、角色、状态(ACTIVE/DISABLED)、默认联系方式、联系方式公开开关、创建时间。
- **Report**（启事，失物与招领共用一张表）：id、type(LOST/FOUND)、标题(物品名)、分类、地点、事件时间(丢失/拾获时间)、描述、状态(OPEN/CLAIMING/RETURNED/HANDED_OVER/OFFLINE/REJECTED/PENDING_REVIEW)、发布者、浏览量、置顶标记、保管方式(FOUND 专用：SELF/AT_SECURITY)、移交单号(可选)、审核信息(审核人/时间/驳回原因)、创建时间。
- **ReportImage**：id、reportId、路径、排序、大小、MIME。
- **Claim**（认领申请）：id、reportId、申请人、方向(APPLY_CLAIM / APPLY_MATCH，用于区分「申请认领别人招领的」与「拾得者认领失物启事」)、独有特征说明、期望交还时间地点、状态(PENDING/ACCEPTED/REJECTED/WITHDRAWN/CLOSED)、处理人、处理时间、拒绝原因。
- **Message**：id、sessionId、发送者、正文、创建时间。
- **ChatSession**：id、claimId、双方用户 id、状态(OPEN/CLOSED)、创建时间。仅认领被接受后创建，只有双方可见。
- **Notification**：id、接收人、类型、关联对象(报告/认领/会话)、是否已读、创建时间。
- **ReportAction**（审计日志）：id、操作人、动作(APPROVE/REJECT/TAKE_DOWN/PIN/UNPIN)、目标启事、原因、时间。
- **ReportFlag**（举报）：id、举报人、目标类型(REPORT/MESSAGE)、目标 id、理由、补充说明、状态(PENDING/RESOLVED/DISMISSED)、处理人、处理结果。
- **ReportView / 统计**：v1 用聚合查询直接算，不建物化表。

### 关键业务规则

- 启事**发布即上线**（状态 `OPEN`）。进入 `PENDING_REVIEW` 的唯一途径是被举报，或由管理员主动下架待复核——不存在「先审后发」的发布前队列，否则内容列表功能无法独立验证。
- 一条启事下，同一用户最多只能有一条非终态（PENDING/ACCEPTED）的认领申请。
- 启事进入 `ACCEPTED` 认领后状态变为 `CLAIMING`；该认领被关闭（CLOSED）或启事被标记 `RETURNED`/`HANDED_OVER` 后，其他待处理申请一并置为 `CLOSED`。
- 认领被接受时，同一条启事上其他待处理申请自动拒绝，并给申请人发通知。
- 只有启事发布者（或管理员）能接受/拒绝自己启事上的认领申请；申请人可撤回自己的 PENDING 申请。
- 「已归还 / 已移交 / 已下架」的启事默认不出现在列表首页，但可在「含已结束」筛选下检索。
- 招领启事发布后可选的「可交还方式」为：自留（走站内会话约定）、已交保卫处（需填移交单号，走线下凭单领取）。

### API 契约（按资源划分，路径为约定而非最终定稿）

- 认证：`POST /api/auth/register`、`POST /api/auth/login`、`POST /api/auth/refresh`、`POST /api/auth/logout`、`GET /api/auth/me`。
- 启事：`GET /api/reports`（支持 type/category/location/timeRange/keyword/sort/page 与 `includeClosed`）、`GET /api/reports/{id}`、`POST /api/reports`、`PATCH /api/reports/{id}`、`DELETE /api/reports/{id}`、`POST /api/reports/{id}/images`、`PUT /api/reports/{id}/status`。
- 匹配：`GET /api/reports/{id}/matches`（基于分类 + 地点 + 时间窗 + 标题相似度的候选列表，纯查询，不落库）。
- 认领：`POST /api/reports/{id}/claims`、`GET /api/claims`（我发起/我收到的，用 `role` 参数区分）、`POST /api/claims/{id}/accept`、`POST /api/claims/{id}/reject`、`POST /api/claims/{id}/withdraw`。
- 会话与消息：`GET /api/chats`、`GET /api/chats/{id}/messages`、`POST /api/chats/{id}/messages`。
- 通知：`GET /api/notifications`、`POST /api/notifications/read-all`、`POST /api/notifications/{id}/read`。
- 管理员：`GET /api/admin/reports?status=PENDING_REVIEW`、`POST /api/admin/reports/{id}/approve`、`POST /api/admin/reports/{id}/reject`、`POST /api/admin/reports/{id}/pin`、`POST /api/admin/reports/{id}/take-down`、`GET /api/admin/flags`、`POST /api/admin/flags/{id}/resolve`、`GET /api/admin/stats`、`GET /api/admin/audit-logs`、`GET /api/admin/export.csv`。
- 分页统一 `{ items, page, size, total }`。

### 前端结构

- Vue 3 + Vite + TypeScript + Vue Router + Pinia。
- 页面：`/`（首页列表）、`/reports/:id`（详情）、`/reports/new`、`/me/reports`、`/me/claims`、`/me/chats/:id`、`/notifications`、`/admin/*`（审核队列、举报、统计）。
- 全部 API 调用集中在一个 `api` 模块（按资源分文件），组件不直接 `fetch`。
- 状态：`authStore`（token/用户）、`notificationStore`（未读数）；列表筛选条件存 URL query，便于分享与刷新保持。
- UI 组件库不引入重型框架，手写基础组件（列表卡片、状态徽标、分页器、表单字段、图片裁剪/预览、空状态）。

## Testing Decisions

**什么算好测试**：只测外部可观察行为，不测实现细节。后端断言「发 HTTP 请求后返回什么、库里最终留下什么」，前端断言「给定 API 返回，用户看到什么、点了什么之后发出什么请求」。不断言私有方法、内部字段命名、SQL 语句本身。

**后端唯一接缝**：REST API 集成测试。用 `@SpringBootTest(webEnvironment = RANDOM_PORT)` + `TestRestTemplate`（或 `MockMvc`）真实跑一遍 Web 层 + Service + Repository，数据库用本机 MySQL 8 的独立测试库 `lostfound_test`（与生产同引擎，避免 H2 语法差异；本机 Docker 守护进程不可用，因此不用 Testcontainers）。每个 ticket 至少覆盖其验收标准里的正向路径 + 一条关键错误路径（如越权接受他人认领、重复申请、对已关闭启事申请）。

**前端唯一接缝**：API client 模块被内存 fake 替换，在页面/组件层做测试（Vitest + Vue Test Utils）。API fake 按后端契约实现同一套形状，因此后端契约变更会同时暴露在两侧测试里。不测内部 store 的私有 action 实现。

**先例**：这是新仓，无既有测试可循；由本 spec 建立两条接缝的既有模式，后续 ticket 复用。

**测试数据**：每个集成测试自带夹具（在事务中建用户/启事），不依赖跨测试共享的种子数据。

## Out of Scope

- 真实投递的短信/邮件通知（v1 只做站内通知；邮件通道留接口不做实现）。
- 校园统一身份认证（CAS / 企业微信 / 微信小程序登录），v1 用学号+密码自建账号。
- 微信小程序端、移动 App。
- Redis 缓存、消息队列、搜索引擎（Elasticsearch）、对象存储（OSS/S3）。

## Further Notes

- 图片上传的存储目录与访问路径需通过配置项注入，本地开发默认 `.data/uploads`，并确保该目录在 `.gitignore` 中。
- 首版不做前端 UI 框架，意味着基础组件的质量直接决定体验；建议把「列表卡片」「状态徽标」「表单字段」做成可复用组件，先在第一个 ticket 里定型。
- 若后续要接 Redisson/RocketMQ 做分布式锁与异步通知（用户技术栈里有），届时把通知投递抽成一个接口即可，不影响 v1 结构。
- 部署形态：单机跑后端 + MySQL，前端静态产物由 Nginx 托管；不做容器编排。提供 `docker-compose.yml` 便于本地起 MySQL。
